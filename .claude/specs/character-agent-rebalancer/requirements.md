# 캐릭터 에이전트 리밸런서 — 요구사항

## 1. Overview

### 문제 정의

온체인 자산 운용은 두 겹으로 막혀 있다.

**첫째, 읽을 수가 없다.** 전략의 성격은 샤프비율·최대낙폭·변동성 같은 숫자로 표현되는데, 이 숫자들은 금융 배경이 없는 사람에게 아무 그림도 그려주지 않는다. "이 전략의 최대낙폭은 22%입니다"를 읽고 자기 성향에 맞는지 판단할 수 있는 사람은 극소수다.

**둘째, 믿을 수가 없다.** 지금 시장에 나온 AI 트레이딩 에이전트 대부분은 LLM이 시장 데이터를 보고 직접 거래를 결정한다. 이 구조에서는 같은 입력에 다른 출력이 나오고, 백테스트가 불가능하며, 과거 성과 기록이 미래 행동을 아무것도 보장하지 못한다. 성과가 좋았다는 주장은 있어도 검증할 방법이 없다.

여기에 수탁 문제가 겹친다. "AI가 대신 굴려준다"는 제품은 대개 자산이나 무제한 권한을 가져가고, 그 순간 사용자는 통제권을 잃는다.

### 목표

**리스크 성향을 캐릭터로 번역하고, 그 캐릭터의 판단을 검증 가능하게 만든다.**

- 각 캐릭터는 **하나의 결정론적 리밸런싱 전략**이다. 같은 시장 상태를 입력하면 항상 같은 판단이 나온다.
- 캐릭터의 모든 판단과 실행은 **온체인에 기록**된다. 트랙레코드는 조작할 수 없다.
- LLM은 **이미 내려진 판단을 설명하는 역할만** 한다. 판단 경로에 개입할 수 없도록 구조적으로 분리한다.
- 자산은 **항상 사용자 지갑에** 있다. 에이전트는 사용자가 정한 한도·기간·대상 안에서만 실행 권한을 갖는다.
- 작은 조정은 캐릭터가 알아서 하고, **한도를 넘는 결정은 멈춰서 사용자에게 승인을 요청**한다.
- 캐릭터의 재량은 고정값이 아니라 **실적으로 버는 것**이다. 잘하면 넓어지고, 못하거나 사용자가 실망하면 좁아진다.
- 에이전트가 일하는 데 드는 비용은 숨기지 않는다. **운영비를 뺀 순성과**가 트랙레코드에 남는다.

### Non-goals

이번 범위에서 의도적으로 제외한다.

| 제외 항목 | 이유 |
|---|---|
| 완전 자율 트레이딩 (무제한 위임) | 투자일임으로 읽힐 수 있고, 신뢰 서사와도 충돌한다 |
| 수익률 예측·목표 수익 제시 | 검증 불가능한 약속이며 규제 위험이 크다 |
| LLM의 거래 판단 참여 | 결정론과 검증 가능성이 제품의 핵심이므로 구조적으로 금지 |
| 메인넷 실자금 운용 | 최소 루프 검증 전 실자금을 다루지 않는다 |
| 자체 토큰 발행 | 제품 검증 전 토크노믹스는 잡음이다 |
| 캐릭터 오리지널 IP 제작 | 무료 샘플 모델로 인터페이스 로직을 먼저 완성한다 |
| 모바일 앱 | 웹앱으로 최소 루프를 완주한 뒤 판단한다 |
| 사용자 간 소셜·랭킹·캐릭터 거래 | 트랙레코드가 쌓인 뒤에야 의미가 있다 |
| 사용자 정의 전략 작성 | 전략 작성 권한은 책임 소재를 복잡하게 만든다 |
| 레버리지·파생·대출 | 리밸런싱 하나를 끝까지 검증한 뒤 확장한다 |
| 처벌·학대 연출 및 관련 아이템 | 지갑 탑재·스토어·실사 전 게이트에서 차단되고, 제품 정체성이 그것으로 고정된다 |
| 신뢰도의 매매 성과 연동 | 결정론(R4)과 트랙레코드(R7)를 무너뜨리며, 성과가 좋아진다는 주장 자체가 거짓이다 |
| 결제를 통한 신뢰도 상승 | 자율성과 연결되는 순간 돈으로 권한을 사는 구조가 된다 |
| 캐릭터 커머스(코스튬·표정팩) | 수익 모델은 최소 루프 검증 후 |
| 신뢰 변화의 연출 확장 | 이번엔 점수 계산과 임계값 연동까지만 |
| x402 실제 결제 연동 | 이번엔 비용 회계와 어댑터 경계까지. 결제 수단은 그 자리에 나중에 끼운다 |
| 자체 x402 facilitator 운영 | 실제 결제를 붙이는 단계의 과제 |

### 성공 기준

아래가 **한 번의 끊김 없는 흐름으로** 동작하면 이번 범위는 완료다.

1. 사용자가 브라우저에서 지갑을 연결하고, 성향이 다른 캐릭터 중 하나를 고른다.
2. 목표 비중과 위임 한도(1회 최대 거래액, 자동 실행 임계값, 유효 기간)를 설정하고 서명한다.
3. 가격이 움직여 목표 비중에서 이탈하면 룰 엔진이 리밸런싱 필요를 판정하고, 필요한 거래 내역을 산출한다.
4. 산출된 거래가 자동 실행 임계값 이내면 캐릭터가 실행하고 사후 보고한다. 초과하면 실행을 멈추고 승인을 요청한다.
5. 실행된 거래가 온체인에 기록되고, 캐릭터의 누적 트랙레코드에 반영되어 화면에서 조회된다.
6. 캐릭터가 판단 근거를 자기 말투로 설명하고, Live2D 모델이 상황(수익/손실/대기/승인요청)에 맞는 표정으로 반응한다.
7. 손실 상황에서 캐릭터의 반응이 사용자를 조롱하거나 축소하지 않는다.
8. 실행 결과가 캐릭터의 신뢰 점수에 반영되고, 그 점수가 다음 판단의 자동 실행 경계를 실제로 움직인다.
9. 사용자가 손실에 실망을 표시하면 캐릭터의 재량이 즉시 좁아지고, 이후 실적으로만 회복된다.
10. 판단에 든 운영비가 기록되어, 화면에 표시되는 성과가 비용을 뺀 순성과다.

추가로 두 가지가 테스트로 증명되어야 한다.
- **동일한 시장 상태 입력에 대해 룰 엔진이 항상 동일한 판단을 반환한다.**
- **신뢰 점수는 판단 내용을 바꾸지 않고 승인 경계만 바꾼다.** 즉 신뢰가 달라도 "무엇을 거래해야 하는가"는 동일하고, "물어볼 것인가 알아서 할 것인가"만 달라진다.

## 2. 요구사항

### R1. 지갑 연결과 체인 중립 동작

**유저스토리:** 온체인 사용자로서, 내 자산을 넘기지 않고 내 지갑으로 이 서비스를 쓰기 위해, 표준 지갑 연결을 원한다.

**인수 조건:**
- R1.1 WHEN 사용자가 지갑 연결을 요청하면, THE SYSTEM SHALL 표준 EVM 지갑 인터페이스로 연결하고 연결된 주소와 체인 ID를 화면에 표시한다.
- R1.2 THE SYSTEM SHALL 사용자의 개인키 또는 니모닉을 어떤 형태로도 수신·저장·전송하지 않는다.
- R1.3 WHEN 사용자가 지원하지 않는 체인에 연결된 상태라면, THE SYSTEM SHALL 실행 기능을 비활성화하고 전환할 체인을 안내한다.
- R1.4 THE SYSTEM SHALL 체인 고유 기능에 의존하지 않고 EVM 표준 인터페이스만 사용하여, 설정 변경만으로 다른 EVM 네트워크에 배포 가능해야 한다.
- R1.5 IF 지갑 연결이 도중에 끊기면, THEN THE SYSTEM SHALL 진행 중인 실행을 중단하고 재연결을 요청한다.

### R2. 캐릭터 선택과 전략 인격

**유저스토리:** 투자 경험이 적은 사용자로서, 숫자를 해석하지 않고도 내 성향에 맞는 운용 방식을 고르기 위해, 성격이 드러나는 캐릭터 중에서 선택하기를 원한다.

**인수 조건:**
- R2.1 THE SYSTEM SHALL 서로 다른 리스크 성향을 가진 캐릭터를 2개 이상 제공하며, 각 캐릭터는 정확히 하나의 전략 파라미터 세트에 대응한다.
- R2.2 WHEN 사용자가 캐릭터 목록을 조회하면, THE SYSTEM SHALL 각 캐릭터의 성향을 서술 문장과 대응 파라미터(허용 이탈폭, 재조정 민감도, 자산군 상한) 양쪽으로 표시한다.
- R2.3 WHEN 사용자가 캐릭터를 선택하면, THE SYSTEM SHALL 해당 캐릭터의 전략 파라미터를 이후 모든 판단의 기준으로 적용한다.
- R2.4 THE SYSTEM SHALL 캐릭터의 전략 파라미터를 런타임에 사용자가 임의 수정할 수 없도록 한다. 성향을 바꾸려면 다른 캐릭터를 선택해야 한다.
- R2.5 WHEN 사용자가 운용 중 캐릭터를 변경하면, THE SYSTEM SHALL 기존 위임을 만료시키고 새 위임 설정을 요구한다.

### R3. 목표 비중과 위임 한도 설정

**유저스토리:** 자산 보유자로서, 에이전트가 어디까지 할 수 있는지 내가 정하기 위해, 실행 범위를 명시적으로 설정하고 서명하기를 원한다.

**인수 조건:**
- R3.1 WHEN 사용자가 포트폴리오를 설정하면, THE SYSTEM SHALL 2개 이상의 자산에 대한 목표 비중을 입력받고, 합이 100%가 아니면 저장을 거부한다.
- R3.2 THE SYSTEM SHALL 위임 설정으로 최소한 다음을 입력받는다 — 1회 최대 거래 금액, 자동 실행 임계값, 위임 유효 기간, 대상 자산 목록, 운영비 지출 한도.
- R3.7 THE SYSTEM SHALL 거래 지출과 운영비 지출을 하나의 위임 예산 아래에서 관리하며, 운영비를 통해 거래 한도를 우회할 수 없도록 한다.
- R3.3 WHEN 사용자가 위임 설정을 확정하면, THE SYSTEM SHALL 온체인 트랜잭션 서명으로 그 설정을 기록하고, 서명 전에 설정 내용 전문을 사람이 읽을 수 있는 형태로 표시한다.
- R3.4 THE SYSTEM SHALL 위임 유효 기간이 지나면 자동 실행을 중단하고 갱신을 요구한다.
- R3.5 WHEN 사용자가 위임 철회를 요청하면, THE SYSTEM SHALL 즉시 자동 실행을 중단하고 온체인 권한을 회수한다.
- R3.6 THE SYSTEM SHALL 위임 대상 자산 목록에 없는 토큰에 대한 거래를 어떤 경우에도 실행하지 않는다.

### R4. 결정론적 리밸런싱 판단

**유저스토리:** 사용자로서, 캐릭터의 과거 성과가 앞으로의 행동을 실제로 말해주기 위해, 판단이 재현 가능한 규칙으로 이루어지기를 원한다.

**인수 조건:**
- R4.1 WHEN 룰 엔진에 동일한 (포트폴리오 상태, 가격 스냅샷, 전략 파라미터) 입력이 주어지면, THE SYSTEM SHALL 항상 동일한 판단 결과를 반환한다.
- R4.2 WHEN 현재 비중이 목표 비중에서 캐릭터의 허용 이탈폭을 초과하면, THE SYSTEM SHALL 목표 비중으로 복귀시키는 데 필요한 거래 목록(자산, 방향, 수량)을 산출한다.
- R4.3 WHILE 이탈폭이 허용 범위 이내인 동안, THE SYSTEM SHALL 어떤 거래도 산출하지 않는다.
- R4.4 THE SYSTEM SHALL 판단 결과에 그 판단을 유발한 수치 근거(자산별 현재 비중, 목표 비중, 이탈폭, 임계값)를 함께 포함한다.
- R4.5 THE SYSTEM SHALL 판단 과정에서 언어 모델·난수·현재 시각에 의존하지 않는다.
- R4.6 IF 가격 데이터를 가져오지 못하거나 데이터가 유효 기간을 벗어났으면, THEN THE SYSTEM SHALL 판단을 수행하지 않고 데이터 부재 상태를 보고한다.
- R4.7 IF 산출된 거래의 예상 비용(가스 + 슬리피지 + 그 판단에 든 운영비)이 리밸런싱으로 교정되는 이탈 가치를 초과하면, THEN THE SYSTEM SHALL 그 거래를 실행하지 않고 사유를 보고한다.
- R4.8 THE SYSTEM SHALL 판단 산출 과정에서 신뢰 점수를 입력으로 받지 않는다. 신뢰 점수가 달라도 산출되는 거래 목록은 동일해야 한다.

### R5. 임계값 분기 승인

**유저스토리:** 사용자로서, 사소한 조정마다 깨우지 않되 큰 결정은 내가 알고 넘어가기 위해, 금액 기준으로 자동 실행과 승인 요청이 갈리기를 원한다.

**용어:** *유효 자동 실행 임계값* = min(사용자가 설정한 자동 실행 임계값, 신뢰 점수로 산출된 현재 재량 한도). 사용자 설정이 절대 상한이고, 신뢰는 그 안에서만 움직인다.

**인수 조건:**
- R5.1 WHEN 산출된 거래의 총 금액이 유효 자동 실행 임계값 이하이고 1회 최대 거래 금액 이내이면, THE SYSTEM SHALL 사용자 개입 없이 실행하고 실행 후 결과를 보고한다.
- R5.2 WHEN 산출된 거래의 총 금액이 유효 자동 실행 임계값을 초과하면, THE SYSTEM SHALL 실행을 보류하고 승인 요청 상태로 전환하며, 사용자가 명시적으로 승인하기 전까지 실행하지 않는다.
- R5.7 THE SYSTEM SHALL 신뢰 점수가 아무리 높아도 유효 자동 실행 임계값이 사용자 설정값을 초과하지 않도록 한다.
- R5.8 WHEN 승인 요청을 표시할 때, THE SYSTEM SHALL 유효 임계값이 사용자 설정과 신뢰 재량 중 무엇에 의해 결정되었는지 함께 표시한다.
- R5.3 WHEN 승인 요청이 생성되면, THE SYSTEM SHALL 거래 내역·금액·판단 근거·임계값 초과분을 사용자에게 표시한다.
- R5.4 IF 승인 요청이 사용자가 정한 유효 시간 내에 처리되지 않으면, THEN THE SYSTEM SHALL 그 요청을 만료시키고 실행하지 않으며 만료 사실을 기록한다.
- R5.5 WHEN 사용자가 승인 요청을 거절하면, THE SYSTEM SHALL 실행하지 않고 거절 사실을 트랙레코드에 기록한다.
- R5.6 THE SYSTEM SHALL 어떤 경우에도 1회 최대 거래 금액을 초과하는 거래를 실행하지 않으며, 초과 시 사용자 승인이 있어도 거래를 분할하거나 거부한다.

### R6. 온체인 실행

**유저스토리:** 사용자로서, 캐릭터의 판단이 실제로 내 포트폴리오에 반영되기 위해, 산출된 거래가 온체인에서 실행되기를 원한다.

**인수 조건:**
- R6.1 WHEN 실행 조건이 충족되면, THE SYSTEM SHALL 산출된 거래를 온체인 트랜잭션으로 제출하고 트랜잭션 해시를 기록한다.
- R6.2 THE SYSTEM SHALL 실행 전에 위임 한도(금액, 기간, 대상 자산)를 온체인에서 검증하며, 한도를 벗어난 실행은 컨트랙트 수준에서 거부되어야 한다.
- R6.3 IF 트랜잭션이 실패하거나 리버트되면, THEN THE SYSTEM SHALL 포트폴리오 상태를 변경하지 않고 실패 사유를 기록하며 사용자에게 알린다.
- R6.4 IF 실제 체결가가 산출 시점 예상가보다 사용자가 설정한 슬리피지 허용치를 넘어 불리하면, THEN THE SYSTEM SHALL 거래를 실행하지 않는다.
- R6.5 WHEN 트랜잭션이 확정되면, THE SYSTEM SHALL 갱신된 포트폴리오 상태를 조회하여 화면에 반영한다.
- R6.6 THE SYSTEM SHALL 동일한 판단에 대해 중복 실행이 발생하지 않도록 방지한다.

### R7. 온체인 트랙레코드

**유저스토리:** 사용자로서, 이 캐릭터가 실제로 어떻게 굴려왔는지 믿을 수 있게 보기 위해, 판단과 실행 기록이 조작 불가능한 형태로 남기를 원한다.

**인수 조건:**
- R7.1 WHEN 캐릭터가 판단을 실행하면, THE SYSTEM SHALL 캐릭터 식별자, 판단 근거 수치, 실행 결과를 온체인에 기록한다.
- R7.2 WHEN 사용자가 캐릭터의 트랙레코드를 조회하면, THE SYSTEM SHALL 온체인 기록을 원천으로 하여 실행 이력을 시간순으로 표시한다.
- R7.3 THE SYSTEM SHALL 트랙레코드 항목을 사후에 수정하거나 삭제할 수 없도록 한다.
- R7.4 THE SYSTEM SHALL 실행되지 않은 판단(승인 거절, 만료, 비용 초과 회피)도 기록하여, 성공 사례만 남는 편향을 방지한다.
- R7.5 WHEN 트랙레코드를 표시할 때, THE SYSTEM SHALL 각 항목에 온체인 트랜잭션으로 검증할 수 있는 참조를 함께 제공한다.
- R7.6 THE SYSTEM SHALL 각 판단에 든 운영비를 트랙레코드에 함께 기록한다.
- R7.7 WHEN 캐릭터의 누적 성과를 표시할 때, THE SYSTEM SHALL 운영비를 차감한 순성과를 대표값으로 제시하며, 차감 전 값만 단독으로 표시하지 않는다.

### R8. 캐릭터 설명 생성

**유저스토리:** 사용자로서, 왜 이 거래를 했는지 이해하기 위해, 캐릭터가 판단 근거를 자기 말로 설명해주기를 원한다.

**인수 조건:**
- R8.1 WHEN 판단이 산출되면, THE SYSTEM SHALL 그 판단의 수치 근거를 입력으로 받아 캐릭터 말투의 설명 문장을 생성한다.
- R8.2 THE SYSTEM SHALL 설명 생성 구성요소가 판단 결과·거래 내역·실행 여부를 변경할 수 있는 경로를 갖지 않도록 한다.
- R8.3 IF 설명 생성이 실패하거나 시간 초과되면, THEN THE SYSTEM SHALL 판단 근거를 템플릿 문장으로 대체 표시하며, 실행 흐름은 중단하지 않는다.
- R8.4 THE SYSTEM SHALL 생성된 설명에 수익률 예측, 목표 수익, 투자 권유로 읽힐 수 있는 표현이 포함되지 않도록 제약한다.
- R8.5 IF 생성된 설명이 판단 근거에 없는 수치를 포함하면, THEN THE SYSTEM SHALL 그 설명을 폐기하고 템플릿 문장으로 대체한다.

### R9. 캐릭터 표현과 손실 상황 톤

**유저스토리:** 사용자로서, 돈을 잃었을 때 조롱당하는 기분이 들지 않기 위해, 캐릭터의 반응이 상황의 무게에 맞기를 원한다.

**인수 조건:**
- R9.1 WHEN 화면이 로드되면, THE SYSTEM SHALL 선택된 캐릭터의 Live2D 모델을 렌더링하고 유휴 애니메이션을 재생한다.
- R9.2 WHEN 상태가 변하면(대기, 판단, 승인요청, 실행완료, 손실), THE SYSTEM SHALL 해당 상태에 매핑된 표정·모션으로 전환한다.
- R9.3 WHILE 포트폴리오가 손실 구간에 있는 동안, THE SYSTEM SHALL 축하·과장된 긍정·유쾌한 표정을 사용하지 않는다.
- R9.4 WHEN 손실을 보고할 때, THE SYSTEM SHALL 손실 사실과 수치를 회피 없이 먼저 제시한 뒤 캐릭터 반응을 덧붙인다.
- R9.5 IF Live2D 모델 로드에 실패하면, THEN THE SYSTEM SHALL 정적 이미지로 대체하고 나머지 기능은 정상 동작시킨다.
- R9.6 THE SYSTEM SHALL 캐릭터 반응이 사용자의 판단이나 손실을 평가·비난하는 표현을 포함하지 않도록 한다.
- R9.7 WHEN 사용자가 실망을 표시하면, THE SYSTEM SHALL 캐릭터가 변명하거나 책임을 시장·사용자에게 돌리지 않는 반응을 표시한다.
- R9.8 THE SYSTEM SHALL 캐릭터에 대한 물리적 처벌·학대를 묘사하거나 암시하는 상호작용을 제공하지 않는다.

### R10. 신뢰 점수와 재량 조절

**유저스토리:** 사용자로서, 캐릭터를 얼마나 믿을지가 기분이 아니라 실적으로 정해지기 위해, 신뢰가 성과에 따라 오르내리고 그만큼 재량이 달라지기를 원한다.

**인수 조건:**
- R10.1 THE SYSTEM SHALL 캐릭터별 신뢰 점수를 온체인 트랙레코드(R7)만을 원천으로 산출하며, 동일한 트랙레코드에서는 항상 동일한 점수를 반환한다.
- R10.2 THE SYSTEM SHALL 신뢰 점수 산출에 운영비를 차감한 순성과와 약속 이행 여부(한도 준수, 승인 절차 준수, 예산 준수)를 반영한다.
- R10.3 THE SYSTEM SHALL 상호작용 빈도, 접속 횟수, 결제 이력을 신뢰 점수 산출에 반영하지 않는다.
- R10.4 WHEN 신뢰 점수가 변하면, THE SYSTEM SHALL 그에 대응하는 재량 한도를 갱신하고 변경 사실과 근거를 사용자에게 표시한다.
- R10.5 WHEN 캐릭터의 운용 성과가 악화되면, THE SYSTEM SHALL 신뢰 점수를 하향하고 재량 한도를 좁힌다.
- R10.6 WHEN 사용자가 손실 보고에 실망을 표시하면, THE SYSTEM SHALL 신뢰 점수를 즉시 하향하고 재량 한도를 좁히며, 그 사실을 트랙레코드에 기록한다.
- R10.7 THE SYSTEM SHALL 실망 표시로 낮아진 신뢰를 이후 운용 실적을 통해서만 회복하도록 하며, 결제·상호작용으로 회복할 수 있는 경로를 제공하지 않는다.
- R10.8 THE SYSTEM SHALL 신뢰 점수가 거래 판단의 내용(대상 자산, 방향, 수량)에 영향을 주지 않도록 한다.
- R10.9 WHEN 신뢰 점수를 표시할 때, THE SYSTEM SHALL 그 점수를 만든 트랙레코드 항목을 함께 조회할 수 있게 한다.

### R11. 에이전트 운영비와 결제 경계

**유저스토리:** 사용자로서, 캐릭터가 일하는 데 든 값까지 알고 판단하기 위해, 운영비가 내 예산에서 투명하게 나가고 성과에서 차감되기를 원한다.

**인수 조건:**
- R11.1 WHEN 에이전트가 유료 자원(가격 데이터, 설명 생성)을 사용하면, THE SYSTEM SHALL 그 비용을 사용자 위임 예산의 운영비 한도에서 차감하고 지출 내역을 기록한다.
- R11.2 IF 운영비 한도가 소진되면, THEN THE SYSTEM SHALL 유료 자원 호출을 중단하고 사용자에게 한도 갱신을 요청하며, 판단을 임의로 수행하지 않는다.
- R11.3 THE SYSTEM SHALL 운영비 지출을 결제 수단과 분리된 인터페이스로 추상화하여, 회계 로직 변경 없이 결제 수단을 교체할 수 있도록 한다.
- R11.4 THE SYSTEM SHALL 검증용으로 배포하는 결제 토큰을 ERC-3009 호환으로 구현하여, 이후 x402 결제 경로를 코드 변경 없이 연결할 수 있게 한다.
- R11.5 WHEN 운영비가 발생하면, THE SYSTEM SHALL 어떤 판단을 위해 쓴 비용인지 해당 판단 기록과 연결한다.
- R11.6 THE SYSTEM SHALL 운영비 지출이 R3.2의 1회 최대 거래 금액이나 대상 자산 제한을 우회하는 경로가 되지 않도록 한다.
- R11.7 WHEN 사용자에게 비용을 표시할 때, THE SYSTEM SHALL 누적 운영비와 그것이 순성과에 미친 영향을 함께 보여준다.

## 3. 제약과 가정

### 제약
- **Live2D Cubism SDK 라이선스**: 무료 샘플 모델과 SDK 사용 조건을 설계 단계에서 확인해야 한다. 상용 배포 시 매출 규모에 따른 라이선스 조건이 붙을 수 있다.
- **체인 중립**: EVM 표준 밖의 기능에 의존할 수 없다.
- **개발 인력**: 1인 풀스택. 병렬 작업 불가, 태스크는 순차 실행을 전제로 한다.

### 가정
- 대상 네트워크에 리밸런싱을 실행할 DEX와 유동성이 존재하거나, 없다면 검증용으로 직접 배포한다. (설계 단계에서 확인)
- 가격 데이터 원천은 결정론적 판단을 가능하게 하는 형태로 스냅샷을 남길 수 있다.
- 수수료 할인은 신뢰 점수에 연동할 수 있으나, 수수료 정책 자체는 이번 범위 밖이므로 신뢰 점수만 산출해두고 할인 적용은 이후 단계에서 붙인다.
- x402는 프로토콜 수준에서 임의의 EVM 체인을 지원하고 facilitator를 자체 운영할 수 있으므로, 체인 중립 설계(R1.4)와 충돌하지 않는다.
- x402 결제 증명 노출과 관련한 프론트러닝 공격이 보고되어 있다. 실제 결제를 연결하는 단계에서 해당 연구를 검토한 뒤 설계한다.
