# soon — 캐릭터 에이전트 리밸런서 아이디어 기획서

- 문서 상태: 승인됨
- 작성일: 2026-09-03
- 상세 요구사항: [requirements.md](./requirements.md)
- 기술 설계: [design.md](./design.md)

## 1. 한 줄 소개

**사용자가 자신의 리스크 성향을 캐릭터로 선택하면, 검증 가능한 규칙과 제한된 권한 안에서 온체인 포트폴리오를 리밸런싱해 주는 비수탁형 에이전트.**

## 2. 기획 배경

온체인 자산 운용에는 세 가지 진입 장벽이 있다.

1. 전략의 성격을 숫자만으로 이해하기 어렵다. 허용 이탈폭, 최대낙폭, 변동성 같은 지표는 금융 지식이 없는 사용자에게 직관적이지 않다.
2. LLM이 직접 거래를 판단하는 에이전트는 같은 상황에서도 다른 결과를 낼 수 있어 행동을 예측하거나 검증하기 어렵다.
3. 자동화 서비스를 쓰기 위해 자산이나 과도한 권한을 넘기면 사용자가 통제권을 잃는다.

soon은 이 문제를 **캐릭터, 결정론적 전략, 온체인 권한 제한**의 조합으로 해결한다.

## 3. 핵심 아이디어

### 캐릭터는 전략 그 자체다

캐릭터의 성격은 장식이 아니라 실제 리밸런싱 파라미터로 연결된다.

| 캐릭터 | 사용자에게 보이는 성격 | 실제 전략 |
|---|---|---|
| 겁 많은 아이 | 조금만 어긋나도 바로 고친다 | 좁은 허용 이탈폭, 목표 비중까지 복귀 |
| 느긋한 아이 | 웬만하면 기다린다 | 넓은 허용 이탈폭, 밴드 경계까지만 복귀 |

사용자는 복잡한 전략 수치를 직접 설계하지 않고, 자신이 감당할 수 있는 행동 성향을 고른다.

### AI는 판단하지 않고 설명한다

거래 내용은 순수한 룰 엔진이 결정한다. LLM은 이미 확정된 수치 근거를 캐릭터 말투로 바꾸는 역할만 맡는다. 설명이 실패하거나 근거에 없는 숫자를 만들면 템플릿 문장으로 대체하며, 거래 흐름에는 영향을 주지 않는다.

### 신뢰는 권한으로 증명된다

캐릭터가 무엇을 거래할지는 시장 상태와 전략으로만 결정한다. 신뢰 점수는 거래 판단을 바꾸지 않고, 캐릭터가 사용자에게 묻지 않고 실행할 수 있는 금액만 조절한다.

- 약속을 지키고 비용을 효율적으로 쓰면 자동 실행 재량이 넓어진다.
- 낭비가 크거나 사용자가 실망을 표시하면 재량이 좁아진다.
- 신뢰가 높아도 사용자가 서명한 절대 상한은 넘을 수 없다.
- 결제나 접속 횟수로 신뢰를 살 수 없다.

## 4. 목표 사용자

### 1차 사용자

- 토큰과 스테이블 자산을 함께 보유하지만 주기적인 리밸런싱이 번거로운 사용자
- 자동화는 원하지만 블랙박스 AI나 무제한 위임은 불안한 사용자
- 금융 지표보다 행동 성향과 구체적인 금액으로 전략을 이해하는 사용자

### 해결하려는 핵심 욕구

> “내가 이해할 수 있는 방식으로 맡기되, 무엇을 왜 했는지 확인하고 언제든 통제하고 싶다.”

## 5. 사용자 경험

1. 사용자가 지갑을 연결한다.
2. 서로 다른 전략을 가진 캐릭터 중 하나를 선택한다.
3. 목표 비중, 1회 최대 거래액, 자동 실행 임계값, 전체 예산과 유효기간을 확인하고 서명한다.
4. 운용 자산을 사용자 소유의 격리 볼트에 예치한다.
5. Keeper가 가격과 잔고를 읽어 결정론적 룰 엔진을 실행한다.
6. 거래가 유효 재량 안이면 자동 실행하고, 넘으면 승인 요청으로 멈춘다.
7. 컨트랙트가 자산·DEX·금액·기간·예산을 다시 검사한 뒤 거래한다.
8. 판단, 실행, 미실행 사유와 운영비가 온체인 이벤트로 남는다.
9. 캐릭터가 Live2D 표정과 자기 말투로 결과를 설명한다.
10. 실행 효율과 약속 이행 기록이 다음 자동 실행 재량에 반영된다.

## 6. 제품 가치

### 이해 가능성

전략을 추상적인 금융 수치가 아니라 일관된 캐릭터 행동으로 보여준다. 동시에 허용 이탈폭과 거래 금액도 함께 표시해 캐릭터 이미지에만 의존하지 않는다.

### 검증 가능성

가격 스냅샷과 포트폴리오가 같으면 룰 엔진은 항상 같은 결정을 만든다. 모든 판단과 실행 결과는 온체인 기록에서 다시 계산할 수 있다.

### 제한된 자동화

작은 거래는 자동화의 편의성을 제공하고, 큰 거래는 사용자 승인으로 되돌린다. 사용자가 서명한 절대 자동 실행 상한과 하드캡은 오프체인 서버가 아니라 스마트 컨트랙트가 강제한다.

### 정직한 성과 표현

캐릭터 성과를 시장 수익률로 포장하지 않는다. 거래 규모 대비 슬리피지와 운영비를 합친 마찰비용을 사용해 캐릭터가 실제로 통제한 실행 품질만 평가한다.

## 7. MVP 범위

### 포함

- 전략 성향이 다른 캐릭터 2종
- 토큰과 기준자산의 목표 비중 설정
- 사용자 소유 AgentVault와 제한 위임
- 결정론적 리밸런싱 판단
- 자동 실행과 사용자 승인 분기
- 온체인 트랙레코드와 신뢰 점수
- 설명 전용 Narrator와 검증 실패 폴백
- Live2D 상태 표현과 정적 이미지 폴백
- 운영비 회계와 단일 예산 강제
- Anvil과 Mock DEX 기반 전체 흐름 검증

### 제외

- LLM의 거래 판단 참여
- 무제한 위임과 완전 자율 트레이딩
- 수익률 예측이나 목표 수익 제시
- 메인넷 실자금 운용
- 레버리지, 대출, 파생상품
- 자체 토큰, 캐릭터 거래, 소셜 랭킹
- 결제로 신뢰도나 실행 권한을 구매하는 기능

## 8. 안전 원칙

| 원칙 | 구현 방식 |
|---|---|
| 사용자 통제권 | 인출 수신자는 항상 볼트 owner이며 위임은 즉시 철회 가능 |
| 이중 한도 검사 | Keeper가 먼저 검사하고 AgentVault가 다시 강제 |
| 결정론 | 엔진에서 네트워크, 시계, 난수 의존 제거 |
| 설명 격리 | Narrator 결과를 실행 함수에 전달할 타입 경로 제거 |
| 기록 재현성 | 데이터베이스 대신 온체인 이벤트를 진실 원천으로 사용 |
| 비용 투명성 | 거래와 운영비가 같은 예산을 사용하고 판단 ID에 귀속 |
| 손실 상황 존중 | 손실 상태에서 축하 표정을 타입 수준에서 선택 불가하게 제한 |

## 9. 수익 모델 가설

MVP에서는 결제보다 제품 신뢰성 검증이 우선이다. 이후에는 다음 두 방식을 검토한다.

- 월 구독: 자동 실행, 기록 조회, 캐릭터 경험에 대한 고정 요금
- 사용량 기반 운영비: 실제 데이터·설명 비용을 투명하게 청구

성과보수와 신뢰도 판매는 제품 원칙과 충돌하므로 제외한다. 실제 결제 수단은 회계 검증 뒤 기존 `PaymentAdapter` 경계에 연결한다.

## 10. 성공 기준

### 제품 완성 기준

- 지갑 연결부터 예치, 위임, 판단, 실행 또는 승인, 기록, 신뢰 반영까지 한 흐름으로 동작한다.
- 같은 입력을 반복해도 같은 판단 ID와 거래 결과가 나온다.
- 신뢰 점수만 바꿨을 때 거래 내용은 같고 승인 여부만 달라진다.
- 실행자 오류나 키 유출 상황에서도 사용자 서명 한도를 넘지 못한다.
- Live2D나 Narrator가 실패해도 자산 운용과 기록 기능은 계속 동작한다.

### 사용자 검증 가설

- 사용자가 두 캐릭터의 실제 전략 차이를 설명할 수 있는가.
- 자동 실행 한도와 사용자 하드캡의 차이를 이해하는가.
- 승인 요청의 이유와 온체인 근거를 확인할 수 있는가.
- 캐릭터 표현이 손실 상황의 심각성을 축소하거나 조롱한다고 느끼지 않는가.

## 11. 현재 상태

2026-09-03 기준으로 웹앱, 룰 엔진, Keeper, AgentVault, 온체인 기록, 신뢰 계산, Narrator, Live2D Haru·Ren의 기반 구현과 TypeScript 테스트 108개가 있다.

요구사항 재검수에서 UI의 캐릭터·목표 비중과 Keeper 설정 연결, 누적 운영비 상한 강제, 캐릭터별 신뢰 분리, 양방향 마찰 계산, 실제 Narrator 호출, 판단·손실 상태 연결이 완료되지 않은 것으로 확인됐다. 기존 73/75 판정은 폐기하고 설계 반영과 재구현 후 다시 산정한다.

## 12. 다음 단계

### 1단계 — MVP 닫기

- 승인된 위임 세션 시작 기준 손익 정책 구현
- UI에서 확정한 캐릭터·목표 비중·한도를 Keeper와 볼트까지 연결
- 누적 운영비 상한과 캐릭터별 신뢰를 실제 데이터 경계에서 강제
- Keeper의 판단 진행 상태를 웹앱에 전달
- 손실 수치 → 캐릭터 반응 순서의 실제 화면 검증

### 2단계 — 테스트넷 파일럿

- owner 지갑의 온체인 승인·거절 흐름 사용성 검증
- 실제 사용자 대상 캐릭터 이해도와 권한 인지 테스트
- 가격, 실행 실패, 비용 데이터를 기반으로 임계값 보정

### 3단계 — 실자금 전 안전 게이트

- DEX 스팟 가격에 TWAP 또는 외부 오라클 교차검증 추가
- AgentVault 외부 보안 감사
- Live2D 상용 라이선스 조건 재확인
- 장애 복구와 운영 모니터링 기준 수립

| 리스크 | 현재 대응 | 다음 대응 |
|---|---|---|

| 손실액 오표시 | 현재 화면에서 손익 표시 보류 | 검증 가능한 기준 가치 기록 |

## 14. 제안 결론

soon의 차별점은 캐릭터 자체가 아니라 **캐릭터로 이해되는 전략, 재현 가능한 판단, 실적으로 제한되는 권한**이다. MVP의 다음 우선순위는 기능 확장이 아니라 손실 기준과 판단 진행 상태를 연결해 현재의 마지막 인수 조건을 닫는 것이다.
