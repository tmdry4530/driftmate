# ADR-0004: 운영비는 회계와 결제를 분리하고, 이번엔 회계까지만 만든다

- **날짜**: 2026-08-31
- **상태**: 개정 승인됨
- **개정일**: 2026-09-03
- **관련 기능**: character-agent-rebalancer
- **관련 요구사항**: R3.7, R4.7, R7.6, R7.7, R11.1~R11.7

## 맥락

에이전트는 판단하려고 가격 데이터를 읽고, 설명하려고 LLM을 호출한다. 이 비용을 사용자 위임 예산에서 지출하기로 했고(R11.1), 순성과를 대표값으로 삼기로 했다(R7.7). x402를 결제 수단 후보로 검토했다.

x402는 이후 결제 수단 후보다. 체인 호환성, 결제 증명 보안과 facilitator 운영은 실제 연결 단계에서 별도로 검토한다.

## 검토한 대안

1. **지금 x402를 실제로 연결한다** — 자체 facilitator를 띄우고 데이터 구매를 실제 결제로 처리한다. 데모가 강해지고 "에이전트가 스스로 지불한다"가 문자 그대로 참이 된다. 그러나 최소 루프에 축이 하나 더 붙어 완주가 늦어지고, facilitator 보안 검토가 선행되어야 한다.
2. **운영비를 아예 다루지 않는다** — 우리가 비용을 부담하고 회계도 만들지 않는다. 가장 단순하지만 R7.7(순성과가 대표값)을 포기하는 것이고, 제품의 "검증 가능한 성과"라는 주장이 반쪽이 된다.
3. **회계와 결제를 분리해 회계만 만든다** — 비용 발생·차감·기록·순성과 계산을 완성하고, 실제 지불은 `PaymentAdapter` 뒤에 둔다. 이번 구현체는 볼트 예산에서 차감하는 내부 정산이고, x402 어댑터는 나중에 같은 인터페이스로 끼운다.

## 결정

**3번을 채택한다.** 그리고 검증용으로 배포하는 결제 토큰을 **ERC-3009 호환**으로 구현한다(R11.4).

핵심 판단은 이것이다 — 제품이 실제로 얻는 가치는 "x402를 쓴다"가 아니라 **"비용을 뺀 성과가 기록에 남는다"**이다. 그 가치는 결제 수단과 무관하게 회계만으로 완성된다. 반대로 회계 없이 결제만 붙이면 아무것도 얻지 못한다.

ERC-3009 토큰을 미리 만들어 두는 비용은 거의 0이다. 어차피 검증용 토큰을 배포해야 하고, `transferWithAuthorization`을 포함시키는 것은 표준 구현을 쓰면 추가 작업이 아니다. 이렇게 해두면 나중에 x402 경로를 붙일 때 토큰을 다시 만들지 않아도 된다.

## 결과

- `PaymentAdapter` 인터페이스: `quote(resource)` → 견적, `acquire(resource)` → payload·확정 비용·영수증. 어댑터는 온체인 장부를 쓰지 않고, 판단 종결 함수가 확정 비용을 기록한다. 이번 구현은 외부 결제 없이 내부 검증 데이터를 반환한다.
- 운영비와 거래 지출은 볼트의 **단일 예산**을 공유한다(R3.7). 운영비 경로로 거래 한도를 우회할 수 없다(R11.6).
- 비용은 판단 ID에 연결되어 기록된다(R11.5). 트랙레코드 조회 시 판단·실행·비용이 한 묶음으로 보인다.
- R4.7의 비용 계산에 그 판단에 든 운영비가 포함된다. 데이터를 사는 값이 교정할 이탈보다 크면 조회 자체를 하지 않는 경로가 생긴다.
- **x402를 실제로 붙이는 단계에서 프론트러닝 관련 연구를 검토한 뒤 facilitator를 설계한다.** 이 부채를 미해결 항목으로 남긴다.

## 2026-09-03 개정

단일 전체 예산과 별도로 `operatingCap`과 `operatingSpent`를 추가한다. 이것은 운영비용 전용 지갑을 따로 만드는 것이 아니라, 모든 지출이 공유 예산을 차감하는 상태에서 운영비에 더 작은 누적 상한을 하나 더 거는 방식이다.

- 거래는 전체 예산만 차감한다.
- 운영비는 전체 예산과 운영비 상한을 동시에 차감한다.
- 어느 한쪽이라도 부족하면 유료 호출을 시작하지 않는다.

가격 데이터 비용은 판단보다 먼저 별도 트랜잭션으로 기록하지 않는다. `executeAuto`, `propose`, `recordNotExecuted` 중 최종 경로가 `Decided`와 가격 비용을 한 트랜잭션에서 함께 기록해, 어느 한쪽만 남는 고아 비용을 막는다.

MVP 가격 어댑터는 유효한 스냅샷과 견적 반환에 성공했을 때만 비용을 확정한다. 실패한 조회는 비용과 판단을 만들지 않는다.

설명 생성 비용은 이미 존재하는 현재 위임의 decisionId에만 연결할 수 있고 decisionId마다 한 번만 허용한다. 비용 기록 트랜잭션이 확정된 뒤 LLM을 한 번 호출하며, 실패·재시작 시 재과금하지 않고 템플릿을 사용한다.

따라서 운영비가 거래 예산을 우회하는 별도 재원이 되지 않으면서 사용자가 입력한 운영비 한도도 실제로 강제된다.
